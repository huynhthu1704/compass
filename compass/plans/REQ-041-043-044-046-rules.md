# Plan — F-015 phase 1, build 1 of 3: Firestore rules and data

Requirements: REQ-041 (AC3), REQ-043 (AC2, rules part), REQ-044 (AC2 and AC4, rules part), REQ-046 (AC1).
Intent: compass/intent/2026-11-27-project-creation-control.md · Design: compass/design/F-015.md (SCR-8, SCR-11) ·
Decisions: ADR-016, ADR-017, ADR-018, ADR-020.

## Why
The phase-1 plan (#117) moves GitHub and Anthropic access to one shared work token and key that only super admins set,
retires project tokens and lets the owner add super admins. The Firestore rules are the security boundary for this
data, so they come first, with the data helpers the next two builds use. No screen changes in this PR.

## Files (7)
- `firestore.rules`:
  - `config/access`: the owner (the hashed email, ADR-013) may update the list of super admins and always stays in it
    (REQ-046 AC1, ADR-018).
  - `config/workspace` (new): work token, Anthropic key, model, auto-sync and the GitHub account for new projects.
    Only super admins write it; super admins and people whose `people/{email}` lists at least one project read it
    (REQ-041 AC3).
  - `people/{email}` (new): the projects a person is on. Each write changes exactly one project id. An Admin of that
    project, or a super admin, adds it only while the project's `members` (after the write) include the email, and
    removes it only when they no longer do. The person reads their own; super admins read all.
  - Each team change adds or removes at most one person, and that person's `people/{email}` must agree after the write;
    a `people` write that changes nothing is accepted (review of #130).
  - `projects/{pid}/secrets/*` stay as they are until build 3, which stops using project tokens and closes them
    (REQ-043 AC2). So these rules are safe to publish as soon as this build is merged.
  - A project's first team stays super-admin only (REQ-044 AC4, ADR-012, unchanged).
- `src/team.ts`: `peopleChanges(before, after)` — who joins and who leaves a team (pure, tested).
- `src/firebase.ts`:
  - `changeTeam` writes `people/{email}` in the same transaction as the team change.
  - `syncPeopleIndex()` — a super admin backfills `people/{email}` for teams created before this change.
  - `loadWorkspace` / `saveWorkspace`, `setSuperAdmins` (owner only) and `deleteOldProjectTokens`, used by builds 2
    and 3.
- `tests/firestoreRules.test.mjs`: emulator tests for TC-079, TC-084 and TC-087 (TC-082 moves to build 3). The old
  cases are updated: the owner may now change config/access, and team changes carry the person's `people` record.
- `tests/team.test.mjs`: `peopleChanges`.
- `compass/spec.json`: REQ-041, REQ-043, REQ-044 and REQ-046 In build; TC-079, TC-084 and TC-087 Pass.
- This plan.

## Steps
plan → rules and emulator tests → pure helper and test → firebase.ts data helpers → checks → review → the PO's yes →
merge → the Product Owner **publishes the rules right after the merge** (see Risks).

## Risks
- **Publish right after the merge:** every merge to main deploys the portal, and the new `changeTeam` writes
  `people/{email}`, which the rules published today refuse. Until the new rules are published, adding or removing
  people on the Team page fails (nothing is half-written; it is a transaction). The new rules keep project tokens as
  they are, so publishing them breaks nothing else. Publish within minutes of the merge.
- **Existing teams have no `people/{email}` yet:** a super admin's next sign-in fills them in (`syncPeopleIndex`, a
  small user-data backfill the Product Owner approves with this PR). Nothing reads the work token before build 2.
- **One project per write:** a first team with several people writes one `people` document per person in the same
  transaction; each is checked on its own.
- **Firestore rule costs:** each `people` write does up to 3 document reads in the rules. That is far below the free
  plan.
